Substituting MPI_Send with MPI_Bsend in the worker processes produced identical hit counts and Pi estimates to Exercise 6 across 1, 2, 4, and 8 processes. Because rank 0 continued to utilize MPI_ANY_SOURCE for its receive operations, incoming data still arrived in a fluid, non-sequential order (for instance, 2, 3, 7, 4, 1, 5, 6 during an 8-process run).
The core operational change involves memory management: MPI_Bsend copies the outgoing data directly into a local buffer previously allocated via MPI_Buffer_attach and returns control immediately. This prevents the worker process from stalling while waiting for rank 0 to issue a corresponding receive. To avoid runtime errors, this application-provided buffer must be spacious enough to accommodate all concurrent, uncompleted messages, accounting for the payload size plus MPI_BSEND_OVERHEAD for every individual message. At the end of execution, decoupling the buffer with MPI_Buffer_detach acts as a blocking operation that ensures all remaining buffered messages are completely delivered before freeing the memory.
In terms of performance, the execution times closely matched Exercise 6, yielding runtime ratios between 0.94 and 1.08 with no distinct advantage. Because each worker process transmits only a solitary integer, altering the underlying send mechanism exerts a negligible influence on the overall application runtime.
